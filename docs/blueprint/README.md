## 为什么这里有、而且不归档

2026-09-20 的文档整理把 `2026-09-08-blueprint-gap-audit.md` 与
`2026-09-08-blueprint-remediation-workboard.md` 移进了 `docs/archive/`。那次移动本身没错
（它们是 9-08 那一轮的**快照**，按归档判据属于历史记录），但**当时没有在活区留下替代品**，
于是"平台当前离蓝图还有多远"这件事从此没有载体：

- 活区只剩 `docs/README.md` 的能力全景表，用的是**另一套口径**（15 个能力域），与蓝图 F01-F27 对不上；
- 9-08 之后工作区累积了 +18409 / -4947 行未提交改动，而对齐状态停在 9-08 没动过。

**闭环断在了"归档"这一环。** 本目录就是补回这一环：这里放**当前**状态，随代码更新；
历史快照仍在 `docs/archive/plans/` 下，两边不重复。

判别标准沿用归档判据：下次动手时还应不应该照它做。对齐计划要照着做 → 活区；
某一次查到了什么 → 归档。

## 权威口径

**功能范围的唯一权威是蓝图**：`orchestrator-enterprise/docs/database-operations-blueprint.html`（另一仓库），
F01-F27 共 27 个模块。平台侧一切"有什么能力"的声明都要能挂到某个 F 编号上。

历史上存在四套独立口径，这是"文档与代码不一致"的结构性来源；当前通过 F 编号对齐：

| 口径 | 数量 | 载体 | 与蓝图的关系 |
| --- | --- | --- | --- |
| 蓝图 F01-F27 | 27 | 另一仓库 HTML | **权威** |
| 文档能力全景 | 15 个能力域 | `docs/README.md` | 已挂 F 编号，不以能力域数量代替模块完成度 |
| 模块开关 | 73 | `backend/app/api/v1/module_config.py` | 配置/权限维度，粒度更细 |
| 运维能力目录 | 15 条 | `backend/app/services/operations_capabilities.py` | 只覆盖会改变库状态的运维动作 |

现在可从[当前差距表](current-gap-assessment.md)按 F 编号查到已实现内容、缺项和源码入口。
备份/恢复的成熟度现从既有备份中心派生，T02 复验不允许登记值覆盖；真实引擎执行仍待验收。文档同步不等于业务或现场验收完成。

## 闭环（loop）

```text
蓝图 F01-F27（唯一权威口径）
   │  文档先行：先写清"要做到什么"
   ▼
对齐计划 alignment-plan.md  ←──────────────┐
   │  按蓝图拆出任务与验收条件              │
   ▼                                        │
代码实现（读代码/改代码）                    │
   │  完成后回到计划更新状态与证据           │
   ▼                                        │
更新文档（能力全景表挂 F 编号）────────────┘
```

每一轮都必须回到计划更新状态，否则计划会在下一次代码改动时失效——这正是 9-08 那份审计的结局。

## 状态口径

沿用 9-08 审计的判据，不要混用：

| 状态 | 含义 |
| --- | --- |
| 主链路具备 | 存在实际处理链，仅表示明确列出的能力具备，**不自动覆盖整个蓝图模块** |
| 部分实现 | 已有功能，同时存在明确缺失、执行断点或语义错误 |
| 缺实现 | 在当前源码中未找到执行路径 |
| 待实机验收 | 代码已有，但证据不足以证明目标版本、权限、负载、故障下可用 |
| 暂缓 | 已明确排除本期 |

另有 **未复核**：本轮未读代码验证，沿用 9-08 结论。**不允许把"未复核"写成"部分实现"**——
两者对读者的含义完全不同。
