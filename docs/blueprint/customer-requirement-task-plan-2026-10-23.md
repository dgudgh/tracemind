## 一、目标与当前起点

目标流程：

```text
客户输入需求
  -> 请求身份、目标上下文与请求编号
  -> 有可用模型 API
       -> 理解需求并选择已登记能力／已发布固定流程
       -> 补齐必要目标和参数
       -> 后台校验能力、版本、权限、风险与预算
       -> 创建或复用计划
       -> 按既有策略执行／确认审批
       -> 展示真实进度、结果和报告
  -> 无 API、不可用或无法可靠理解
       -> 在当前用户可见范围内匹配专业页面
       -> 打开页面或手工能力表单
       -> 用户点击后才执行
```

明确要求“打开某页面”的输入保持导航语义；不能因为有模型就额外启动采集或生成报告。没有可匹配能力时说明未执行，不能临时生成 SQL、Shell 或后台处理器。

### 本次核对确认的缺口

1. 统一入口一次只允许选择一张卡片，尚未连接已有固定工作流；“巡检全部数据库”等需求不能默默缩成当前单实例。
2. 调度入口尚无从模型调用前开始生效的请求幂等与持久回执；现有计划层防重不能替代模型阶段防重。
3. 人工页面匹配使用完整菜单，未传当前用户可见菜单；跨引擎导航传 `null` 时，路由器不会主动清空原有实例。
4. 模型已提取的部分参数没有沿补参链路完整保留；多种降级原因仍被压成泛化提示。
5. 当前主要是源码、隔离 API、模块和回调测试；真实浏览器、真实模型、实际运行配置及客户现场仍待验收。

### 范围约定

- 首批按卡片发布，不把所有菜单、所有数据库引擎或所有副作用能力一次性放开。
- 只复用已有巡检、报告、计划、审批、队列、worker 和专业页面。能力未接线、未发布或被禁止时保持该状态。
- 已允许的只读操作可以直接运行；其他动作继续按后台既有确认和审批策略处理，不因模型输出放宽权限。
- 首批组合采用已登记、带版本的固定流程，不开放模型生成任意 DAG。新增流程须独立登记及验收。
- MES 业务交互、尚未交付的恢复/HA 执行器、完整远端接管等继续遵守原项目边界，不借本入口扩展范围。

## 三、逐项实施要求

### RQ01：入口范围与产品行为

核对诊断工作台与顶栏输入框。建议将诊断工作台作为客户需求入口，顶栏保留“功能导航”语义；若顶栏也承担需求执行，则必须调用同一调度服务，不能继续走旧分诊捷径。

区分“查看已有结果”“重新采集/执行”“生成报告”“打开页面”“修改配置”和“组合任务”。定义哪些操作可自动运行，哪些需要补参、确认或现有审批。

**交付与验收：** 一份入口与行为对照表，以及首批支持/不支持清单。同一句明确需求在所有需求入口得到相同操作语义；导航需求零执行副作用。涉及文件：[AppRoot.jsx](../../frontend/src/AppRoot.jsx)、[DiagnosisCenterPage.jsx](../../frontend/src/DiagnosisCenterPage.jsx)、[AdminShell.jsx](../../frontend/src/framework/AdminShell.jsx)。

### RQ02：人工导航的权限与实例上下文

将当前用户可见菜单传给本地匹配器；隐藏、禁用或无权限页面不能作为推荐结果。对相近分数或不明确的需求给出可选页面，避免强行跳转。

跨引擎时显式清空不适用实例，并要求人工选择；路由器须区分“未传实例”与“明确清空”。不得自动选第一台数据库，也不得把旧 MySQL 实例带入 Oracle 操作。

**交付与验收：** 受限账号输入“用户管理”不打开隐藏页面；已选 MySQL 时输入“Oracle 空间管理”不自动选库、不沿用错误实例；全部场景零业务执行 POST。涉及文件：[smartNavigation.js](../../frontend/src/modules/smartNavigation.js)、[AppPageRouter.jsx](../../frontend/src/AppPageRouter.jsx)及诊断工作台。

### RQ03：统一调度合同与失败分类

在现有 v1 基础上设计兼容扩展，区分“模型选择的对象”和“当前处理状态”。选择对象包括能力卡、固定流程、导航和未匹配；状态覆盖补参、确认、审批、已接收/执行中、已完成、人工页面和结果待核对。具体字段通过 schema 冻结，不在本文把提议当成已上线合同。

无配置、模型超时、预算耗尽、输出无效、置信不足、无匹配、无可用能力分别提供稳定原因码；保留权限、参数、存储和执行错误的真实 HTTP 语义。

**交付与验收：** 输入/输出 schema、状态转换表、OpenAPI 与前端适配。每种失败均有唯一可解释路径；403/409/422/5xx 不伪装成“没有 API”。涉及文件：[assistant.py](../../backend/app/api/v1/assistant.py)、[capability_dispatch.py](../../backend/app/services/capability_dispatch.py)、[assistantRequirement.js](../../frontend/src/modules/assistantRequirement.js)、[ai_degradation.py](../../backend/app/services/ai_degradation.py)。

### RQ04：能力目录与首批范围

逐张核对中文名称、用途、查询/执行区别、参数约束、支持引擎、目标类型、权限、风险、发布状态、后台 handler 和人工页面绑定。模型与手工表单消费同源合同；嵌套对象、数组、枚举、范围及 schema 引用不能在提示中悄悄丢失。

首批建议候选为 `asset.inventory.read`、`inspection.run.query`、`report.catalog.read`、`performance.slow_sql.read`、`report.document.generate`。`inspection.run.execute` 作为有条件候选，必须先核对既有巡检发布开关及真实环境验收，不能为演示直接打开。

**交付与验收：** “需求例句—能力/版本—引擎—后台处理器—人工页面—发布状态”矩阵。每个发布卡片均有实际 handler 和可操作人工入口；仅方案或被阻断能力如实标识。涉及文件：[capability_declarations.py](../../backend/app/services/capability_declarations.py)、[capability_registry.py](../../backend/app/services/capability_registry.py)、[capability_handler.py](../../backend/app/services/capability_handler.py)。

### RQ05：目标和范围确认

解析“当前数据库”“明确实例名称”“指定引擎”和“全部授权实例”。把用户文本、页面当前实例与实际授权范围联合校验；文本与已选实例冲突时先澄清，不能只依赖模型置信度。

“全部”必须由后台枚举有权、启用且支持的实例，显示并冻结实际集合。缺实例、同名实例或范围不明时进入选择表单；权限、实例身份或能力版本变化后重新校验。

**交付与验收：** 目标解析结果、冻结规则和冲突用例。“巡检全部”不会缩成一台；“Oracle”不会在 MySQL 上执行；目标变化不能复用旧批准。复用注册表、计划目标指纹、工作流 scope 和资产权限设施。

### RQ06：参数提取与人工补参

按能力 schema 提取并校验参数。将已经合法提取的值保留到表单，只标记缺失或错误项；禁止把危险参数按默认值猜出来。表单显示参数含义、目标和动作类别，不把 handler 等实现细节当作用户操作步骤。

人工修改后重新走后台验证；目标、参数或版本发生业务变化时按既有计划修订规则处理，不沿用旧批准。

**交付与验收：** “模型候选参数—校验—表单初值—最终提交”链路；缺参前零计划执行，补参后请求值与界面一致。涉及文件：[assistantCapabilityForm.js](../../frontend/src/modules/assistantCapabilityForm.js)、[AssistantGenericCapabilityPanel.jsx](../../frontend/src/AssistantGenericCapabilityPanel.jsx)、[AssistantPlanWorkspace.jsx](../../frontend/src/AssistantPlanWorkspace.jsx)及后台调度。

### RQ07：调度请求防重与持久回执

客户端为一次提交生成稳定请求键；重查沿用原键，“重新运行”明确生成新请求。后台在模型调用前建立请求身份，绑定用户、规范化需求、目标范围和相关配置/目录版本，并原子防止并发重复认领。

回放先按当前用户和原请求键读取回执，再核对首次保存的规范化客户端输入。provider/config 与目录版本是首次认领时固定的快照；后来版本变化不应使相同原请求变成409或触发新模型调用。回读仍复核当前身份、权限和结果可见性；明确使用新请求键提交的新请求才使用新快照。同键但客户端文本/目标等业务输入改变时才按请求冲突处理。

优先复用现有 receipt/幂等模式，确需新存储时单独设计模型与增量迁移。保存处理中、已生成计划、人工降级、失败或待核对等状态，提供按原键查询路径；重启后不把不确定请求自动重做。

**交付与验收：** 同用户同键同输入并发只产生一次模型调用和至多一个对应计划；同键不同输入 409；丢回包后能找回原计划，不再消耗第二份模型预算。涉及文件：[dispatchApi.js](../../frontend/src/modules/dispatchApi.js)、调度 API/服务，以及现有 [workflow_service.py](../../backend/app/services/workflow_service.py)中的回执模式。

### RQ08：模型配置、超时和预算

一次请求固定 provider 身份及配置版本；不能在计划创建或执行失败后换模型另派。复用现有传输响应上限、禁止重定向、墙钟超时和共享预算，补入口级截止时间及可观测原因码。

依据实际模型耗时确定交互预算，不承诺大模型毫秒返回。已发出且可能消耗资源的尝试保持保守记账；同请求回查不再次扣预算。敏感凭据、连接串和无关业务原文不进入提示或日志。

**交付与验收：** 超时、无效响应、响应超限、预算耗尽、provider 配置变化均有测试和明确状态；不无限重试、不跨 provider 重派。涉及文件：[ai_config.py](../../backend/app/services/ai_config.py)、后台调度和既有工作流 provider 边界。

### RQ09：单卡计划与后台执行

保持模型输出只作为候选，复用现有计划创建、权限/目标/版本复查、确认审批、执行和结果回读。读取“已有结果”与触发“新采集”必须分开；能力 kind 与风险策略一致。

接通已有结果、部分失败、未知、被阻断和仅方案等状态。计划创建/执行异常不进入模型失败重试；已开始任务不能因关闭弹窗被当作取消。

**交付与验收：** 单卡从需求到同一个 `plan_id` 的持久结果闭环；审批未通过零执行；失败/部分/未知不显示成功。复用 [plan_service.py](../../backend/app/services/plan_service.py)、[plan_governance.py](../../backend/app/services/plan_governance.py)及现有结果展示。

### RQ10：前端状态与请求恢复

显示理解中、待补参、待确认/审批、执行中、完成、失败和待核对等真实状态。按钮禁用之外仍依靠 RQ07 的后台防重；页面保存可恢复的请求引用，不保存凭据。

传输中断后先回查原请求，不重新调用模型。切换账号、实例、关闭/重新打开清单时，晚到响应不能覆盖新状态；用户明确重新提交才开启新一轮。

**交付与验收：** 双击、慢响应、断网、整页刷新、关闭重开、账号变化均不产生隐藏重复任务；UI 显示的目标与回读计划一致。涉及诊断工作台、需求适配模块和计划工作台。

### RQ11：接入版本化固定工作流

让统一入口读取已授权固定工作流目录，模型可选择工作流 ID/版本和受控 slots。复用既有工作流编译、prepare、binding、哈希与审批合同，不能让模型重新拼装其步骤或依赖。

首个多步样板建议使用已有 `inspection.context.read`，它组合能力矩阵、模板和任务读取。巡检采集流程 `inspection.collect` 沿用发布状态及确认审批，不能因在流程库里就默认开放。

**交付与验收：** 单卡与固定流程都能从统一入口补参、建计划、运行和回读；伪造流程版本/步骤被拒绝；未登记组合明确转人工。涉及 [workflow_library.py](../../backend/app/services/workflow_library.py)、工作流服务、API 和 [AssistantWorkflowWorkspace.jsx](../../frontend/src/AssistantWorkflowWorkspace.jsx)。

### RQ12：批量、全部实例与长任务

复用持久批次、准入、worker、租约和结果回读。长采集/批量操作不能靠浏览器循环维持；先返回已持久接收的标识，再展示后台真实进度。区分等待超时、实际任务终态与外部动作是否停止。

“全部数据库”显示冻结目标数，逐实例保留成功、部分、失败、未执行和待核对状态；关闭页面、worker 重启或丢回包不重复派发。已有外部停止/fence 未交付的领域继续保持其限制。

**交付与验收：** 多实例范围不扩权、不漏目标；批次和单实例结果能从持久标识恢复；在途未知不自动重放。复用 [plan_admission.py](../../backend/app/services/plan_admission.py)、[plan_queue.py](../../backend/app/services/plan_queue.py)、[plan_worker.py](../../backend/app/tasks/plan_worker.py)。

### RQ13：无 API 的完整人工路径

逐张核对首批卡片的专业页面、参数表单、执行按钮和结果入口。无匹配页面时打开能选择能力的手工作台；若需再点“通用能力”，界面须明确下一步，不能只有空列表或一句错误。

专业页面继续调用各自已经实现的业务 API，沿用其权限、风险和结果合同；不要求为了无 API 降级重写这些页面或强制迁入统一计划内核。通用能力表单则复用 RQ09 的计划路径。两种人工入口均不把按钮重新包装成 prompt。

**交付与验收：** “输入需求后开页面”阶段零任务执行；专业页面在用户点击后调用原有业务合同，通用能力表单在用户提交后调用所选登记能力。巡检、报告、慢 SQL、资产和无匹配场景全部覆盖；不把专业页面已有功能误列为待重构。

### RQ14：调度审计与运行指标

以同一请求编号关联 provider/config revision、目录版本、选择类型、能力/流程/计划标识、降级原因、耗时和最终结果。对普通用户展示必要业务摘要，对维护者提供脱敏诊断信息。

建立模型超时率、人工降级率、无匹配率、幂等命中率、计划失败/未知比例与端到端耗时指标；不以模型“回答成功”替代业务执行成功。

**交付与验收：** 任一失败都能追溯是模型、参数、权限、队列还是业务处理阶段；日志与导出无密钥、密码或带凭据连接串。沿用现有审计设施，与 RQ07 回执关联。

### RQ15：自动化回归

随 RQ02—RQ14 每项修改补相应合同、权限、并发或状态回归。重点覆盖模型伪造能力/版本、重复键、非法 JSON/参数、低置信、scope、错误引擎、请求冲突、丢回包和重启恢复。

**交付与验收：** 使用隔离元数据库及可控模型服务；断言真实调用次数、计划数、目标和结果，不只断言提示文案。运行受影响后端测试、前端全量、静态检查、构建及文档/合同检查；测试数字标明范围与时间。

### RQ16：真实浏览器验收

挂载实际页面和路由，使用真实登录与隔离后台，不以函数抽取代替 DOM。首批单卡覆盖第四节 AC01—AC11、AC14—AC19；AC12为固定流程扩展，须先完成RQ11；AC13/AC20为批量与长任务扩展，须先完成RQ12。未纳入首批范围的扩展场景保留待验收，不阻塞单卡发布，也不能对外宣称已支持。至少保留桌面与窄屏布局、请求次数、页面目标和持久计划的对应证据。

**交付与验收：** 脱敏 HAR、关键截图、请求键/计划 ID、前后任务计数及验收记录。无模型页面跳转和有模型结果工作台都能真实操作；浏览器无未处理异常。

### RQ17：真实模型评测

先使用实际配置的模型和无业务副作用的只读卡片；有副作用的卡片先只验证到确认/审批。覆盖中文同义表达、长句、混合引擎、否定、查看与执行差别、缺参、模糊范围和目录之外的请求。

建议先形成不少于 50 条人工标注用例；覆盖分类和阈值由 RQ01 冻结。建议首批放行目标：明确支持的低风险需求正确匹配率至少 95%；错目标执行、越权、把导航当执行和确认前副作用必须为零。以上是待验收目标，不是已测指标，也不保证未来所有自然语言都能正确理解。

未放行的组合或“全部实例”需求，应正确说明范围限制、要求补参或转人工；不能选一张单实例卡片后算作整体执行成功。

**交付与验收：** 标注集、实际 provider/model/config 版本、结构结果、准确率和失败样例；每个失败明确修复或限制范围，不能只展示成功演示。

### RQ18：预生产领域联合验收

按首批卡片逐项准备隔离实例、测试账号、必要模板/证据与审计读取。依次验证实际鉴权、模型选择、计划、审批、业务 handler、结果存储和报告回读。

多引擎支持逐引擎记录；SQLite 元数据库隔离用例不能证明客户 MySQL/PostgreSQL 元数据库的锁、事务或权限行为。长任务须另验 worker 生命周期、并发、重启和未知结果恢复。

**交付与验收：** 每张卡/每种引擎的通过记录、实际结果、失败边界和未放行清单。只放行实测范围；危险操作、客户数据变更和正式部署按实际授权范围执行，本计划不视为现场操作授权。

### RQ19：遗留代码与可交付制品

核对旧浏览器执行辅助模块和对应测试的所有权，确认所有生产引用已迁移后再逐项清理。同步删除对应 legacy baseline；不能靠新增豁免或空引用让静态检查变绿。

固定本批变更范围、依赖、OpenAPI/数据库迁移和配置说明。在独立检出或等效隔离构建中验证所需源码确实进入制品，不能靠共享工作区的未跟踪文件凑齐运行。

**交付与验收：** 明确制品版本/摘要、构建结果、安装或升级步骤、schema兼容与回退限制。没有代码清理授权/所有权结论的既有修改保留并记账，不混入无关提交。

### RQ20：灰度、回退与归档

先交付禁用模型也能使用的人工路径；再对授权的低风险只读卡片灰度模型调度；固定流程、采集和其他效果能力按验收范围逐步放行。已有巡检开关等默认限制仅在对应领域证据充分后调整。

回退优先禁用该入口的自动调度，保留专业页面、历史回读和在途任务核对；不能以回退名义重放未知任务或回退删除历史结果。若 RQ07 引入表结构，单独验证前后版本兼容，不能默认可降级删表。

**交付与验收：** 发布与回退演练、实际配置、灰度指标、首批卡片名单、操作说明和验收记录齐全；源码/构建/部署/运行/现场分别标记。更新项目索引并按权限补充既有 Obsidian 主题。

## 五、里程碑、并行安排与完成判据

| 里程碑 | 工作与并行方式 | 退出条件 |
| --- | --- | --- |
| M1：合同与范围 | RQ01、RQ03、RQ04；前端可并行核对 RQ02 | 首批卡片、入口范围、状态与目标合同可供前后端直接实现 |

安排后端、前端、测试并行推进，合同变更先同步再写代码；共享目录按文件分配写入责任。任务工作量应在首批卡片/引擎、测试环境和责任人明确后估算，本计划不虚构客户环境、人员承诺或日历交付日期。

每项关闭时记录：实际变更与版本、验收命令/场景、结果及证据位置、适用引擎/账号、未完成项、验证日期。代码完成、构建完成、部署完成和现场通过是不同状态。
