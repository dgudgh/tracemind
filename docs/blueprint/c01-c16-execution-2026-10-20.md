不是执行证据。缺证据不生成完整健康分；历史 DTO 投影不回写客户旧记录。

实际 SQLite/API 检查还发现并修复：任务时间字段被 JSON 转成字符串导致入库失败、POST/
GET finding 顺序不一致。引擎读取/报告/AI-input/ticket 使用同一持久读取投影。
直接 ORM 消费者 `ai_evidence` 与 `suggestion_aggregator` 的旧分数旁路继续一并复核，
不因仅引擎测试通过就关闭 ISS-58。消费者、覆盖清单完整性与最终复核证据在收口后补录。

## C14：审批写动作的第一条真实路径（2026-10-21）

写动作不是"再挂一个 handler"。计划执行对 effect 的取证是**按能力硬编码**的：
`validate_effect_reference` 只认 `kind == "inspection_job"` 并有对应 `DBInspectionJob`，任何
第二条 effect 都会在取证阶段被判 `result_unknown`。本轮先把这一层打通，再接第一条写动作。

- 结果引用区分三类：`inspection_job`、`capability_effect`、`capability_read`。
- effect 取证按能力分派：`monitor.capacity.execute` 的证据是**容量策略行本身**——
  `last_run_time` 必须不早于本步开始时间，成功时 `last_status == "success"` 且
  `last_sample_count` 与返回值一致；`skipped`/`no_data` 只能是 `partial` 且原因码必须与行状态对应。
  **旧行（时间早于本次运行）一律 `result_unknown`**，避免拿历史快照冒充本次结果。
- handler 侧同样不信任自己：先过 fence，再采集，再复查 fence；`skipped/no_data` 不返回 success。
- 审批链按原语义：`create_plan` 后 `approval_state=pending`，未批准执行直接 `approval_required`；
  批准人与请求人必须是不同账号（`self_approval_forbidden` 保留）。

**主动收回的一条**：`performance.suggestion.refresh` 本来也接上了，但 `rebuild_suggestions`
在没有数据源时合法返回 0，**没有任何行级证据能区分"真的重建了"和"被跳过"**。按本仓
"没有证据不算成功"的底线，把它退回 `declared_not_wired` 并写明原因，而不是留一个永远绿的写口。

证据：`test_capability_effects_c14.py` 11 项，覆盖：无 durable execution 拒绝、fence 在写前后各查一次、
fence 抛错时服务零调用、skipped/no_data 不报成功、未批准执行拒绝、只读账号拒绝、
**完整链路（请求人建计划 → 另一管理员批准 → 带 fence 执行 → 证据校验 → 回读一致）**、
以及"陈旧证据被拒"的反例。联合：声明 12、c01 契约 236、巡检工作流+队列 75。

**仍未做**：其余采集/同步/扫描类（`performance.*.collect`、`monitor.*.sync/bind/scan`、
`asset.discovery.execute`、`governance.candidate.scan`、备份/恢复计划与执行）以及
`operations.startup/shutdown/switchover` 计划类；它们各自需要"域内证据"定义，
不能共用容量快照那条规则。

## C16：发布门禁与长稳探针（2026-10-21）

C16 原来是"零"：没有 CI、没有压测/长稳脚本。本轮补的是**判据与工具**，不是结论：

- `scripts/release_gate.py`：把四条质量底线拆成四个证据层（static / local-http / real-engines /
  soak）。**缺证据 = `not_executed`，永远不会被算成通过**；`--expect-hours` 默认 168，
  所以"跑 20 分钟 soak 然后不提要求"这条路走不通（实测：0.0008h 的 soak 被判 failed）。
- `scripts/soak_probe.py`：真实 HTTP 探针，记录 p50/p95/p99/max、失败样本与失败数，不重试、
  不隐藏失败；实测 3 秒 6 次探测通过并写出证据。
- `.github/workflows/ci.yml`：后端 pytest + `check_all.py --fast`，前端 `node --test` + build。

当前真实判定（本机实际跑了前两层，后两层没有环境）：

```
release gate — blocked
  static        passed        # python scripts/check_all.py --fast → All validation checks passed
  local-http    passed        # 隔离后端 18821 + 12 次真实探针，0 失败，p95 6.6ms
  real-engines  not_executed
  soak          not_executed
```

两层通过、两层缺证据，判定仍是 blocked——这正是门禁应有的行为。

**未做且不能由本轮声明**：托管 CI 实跑、四引擎现场采集、故障注入、毫秒级分项时延、
168 小时长稳、候选包与部署回退。门禁的存在只证明"没人能伪造发布"，不证明"可以发布"。
