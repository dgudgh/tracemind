# 需求交付测试执行与验收发布操作分册

日期：2026-10-25

适用范围：客户需求 R01-R12 的开发候选版测试、验收、升级、灰度和发布退出判断。开发任务 D01-D18 与测试用例 TC001-TC116 的详细定义由并行分册维护；本分册只规定执行方法、环境、证据和门禁，不替代需求、任务或用例正文。

状态：**执行手册草案；本轮未调用真实模型、未连接真实目标数据库、未执行平台库迁移、未做完整备份恢复或 168 小时长稳。**

## 1. 当前基线与证据边界

截至 2026-10-25，已知运行基线为：平台控制库是 MySQL 8.0.40；后端 8800 健康检查返回 200；该控制库尚无 `db_capability_effect_receipt` 表，迁移记录中也尚无 `20261023_01_capability_effect_receipt`。因此“服务健康”不能解释为本轮需求已具备执行回执或已完成升级。2026-10-23 的真实模型首轮结果仍为 `invalid_output`，不得登记为模型验收通过。历史自动化测试使用过模型替身和受控 collector，只证明隔离合同或编排路径，不证明真实模型理解质量、真实目标库查询结果或真实副作用。

本分册采用两个独立结论：

- **开发候选就绪（development candidate ready）**：R01-R12 对应代码、合同、L1-L3 和规定的非生产端到端测试完成，D01-D17 无阻断开发缺陷，D18 中可在发布前完成的发布准备项已完成，TC001-TC116 中适用于该阶段的必测项全部通过。它表示候选代码可进入 L4 和发布阶段 P，不代表真实外部能力或生产交付完成。D18 中必须在实际灰度、回退和长稳后取得的证据，在生产发布时关闭。
- **生产发布（production release）**：同一不可变候选制品完成 L1-L4，并完成独立发布阶段 P 的平台 MySQL 升级、恢复演练、灰度、回退验证和 168 小时长稳；所有发布必测项都有可追溯证据。只有这一结论可用于发布放行。

任一必测项为 `blocked`、`not_run`、`not_executed`、无可读证据或证据未绑定当前候选时，生产发布结论只能是 **blocked**。

## 2. 四层验证与环境矩阵

### 2.1 分层定义

| 层级 | 目的 | 允许的替身 | 必须使用的真实对象 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- | --- | --- |
| L1 源码与隔离合同 | 静态检查、单元测试、权限/参数/状态机/失败关闭合同、前端逻辑 | SQLite、模型 stub、collector stub、合成时钟 | 当前源码、锁文件和构建工具链 | 代码合同和确定性回归 | MySQL 并发语义、真实模型、真实目标库、浏览器体验、发布可恢复性 |
| L2 服务集成 | 真实 HTTP、独立 MySQL 控制库、真实 worker、队列与持久回读 | 模型和 collector 可以明确标记为 stub | 实际后端进程、worker 和独立 MySQL 控制库 | API、权限、队列、并发、回读和 MySQL 控制面组合可工作 | 浏览器交互、真实模型、真实目标库 |
| L3 浏览器与组件路由 | 从真实浏览器经过实际前端组件、路由和 HTTP 到独立 MySQL 控制库 | 仅在用例明确只验证 UI 时，模型或 collector 可标记为 stub | 实际浏览器、候选前端、候选后端、worker、独立 MySQL 控制库 | 页面状态、路由、交互、持久状态和失败展示一致 | stub 对应的模型理解或目标采集真实性 |
| L4 真实外部闭环 | 授权的真实模型、真实目标库、MySQL 控制库、实际能力执行与结果/回执 | 关键边界不得 stub；模型、collector、目标执行器和回执均用真实对象 | 授权模型 API；隔离真实 Oracle/MySQL/PostgreSQL/SQL Server 目标 fixture；独立 MySQL 控制库 | “理解 → 校验 → 现有能力实际执行 → 持久结果/回执”成立 | 生产迁移、灰度、回退和 168 小时长稳 |

升级、备份恢复、灰度、回退和 168 小时长稳统一记为**发布阶段 P**。P 是发布过程与环境维度，不是第五个测试层级，也不占用 L4；它消费已通过的 L1-L4 证据，并在预生产和生产灰度环境验证候选的可发布性。

### 2.2 环境矩阵

| 环境 | 平台控制库 | 被管理目标库 | 模型 | 主要层级 | 数据处置 |
| --- | --- | --- | --- | --- | --- |
| E0 本地隔离 | SQLite 临时文件或内存库 | collector stub / 合成实例 | stub 或禁用 | L1 | 测试结束删除临时文件 |
| E1 MySQL 控制库集成 | 独立 MySQL schema，版本与生产兼容；仅供本候选使用 | 合成实例行，不建立现场连接 | stub、禁用或受控假响应 | L2；加真实浏览器后可执行 L3 | 用例级创建；按白名单清理 |
| E2 真实能力实验室 | 独立 MySQL 控制库 | 每种引擎独立的可丢弃真实实例/数据库/账号 | 经授权的真实模型 | L4；也可复跑 L2-L3 | fixture 有基线快照、唯一前缀和确定性清理 |
| E3 预生产 | 生产拓扑等价的 MySQL 控制库副本 | 授权的真实非生产目标实例 | 授权的真实模型 | L1-L4 回归 + 发布阶段 P | 备份、恢复、审计和保留策略均实际演练 |
| E4 生产灰度 | 生产 MySQL 控制库 | 明确批准的灰度实例集合 | 经批准的生产模型配置 | 发布阶段 P；按需抽验 L4 | 只在变更单范围内执行；逐阶段人工晋级 |

“平台控制库”保存账号、计划、队列、审批、审计、结果和执行回执；“目标库”是被平台读取或操作的 Oracle/MySQL/PostgreSQL/SQL Server。两者必须分别登记主机指纹、引擎、版本、库名、账号用途和销毁策略，证据中不得混写。E0 的 SQLite 通过不能替代 E1-E4 的 MySQL 控制库终验；目标库使用真实 MySQL，也不能弥补平台控制库仍为 SQLite 的缺口。

## 3. 账号、数据、fixture 与清理

### 3.1 测试身份

每个环境至少准备以下互不共用的身份，并在证据中记录内部 ID 和角色，不记录密码、令牌或连接串：

| 身份 | 用途 | 最小权限及关键验证 |
| --- | --- | --- |
| requester | 提交普通读取和效果动作 | 只能看授权实例；不能批准自己的高风险动作 |
| approver | 独立审批 | 不兼任本用例 requester；批准必须绑定计划 revision、目标和参数摘要 |
| operator | 启停 worker、执行迁移和恢复演练 | 不作为日常应用账号；仅在维护窗口临时使用 |
| reader | 只读与无权场景 | 读取授权资源；写、审批、跨实例访问均拒绝 |
| disabled / revoked | 会话撤销回归 | 禁用、改密或撤销后旧令牌和在途新动作应失效 |
| worker identity | 队列认领与执行 | 与人类账号分开；认领、租约、fencing 和回执可审计 |

账号和授权关系必须由 fixture 或受控初始化脚本建立，不能借用个人生产管理员账号。审批类用例保留 requester 与 approver 两个不同主体。

### 3.2 合成业务数据

控制库数据至少覆盖：12 条需求对应的可见/不可见能力；四种引擎实例；正常、禁用、越权和失联实例；需要参数、缺参数、错误参数和跨范围参数；读取、采集、可逆效果、高风险效果；待审批、批准、撤销、过期、取消、租约丢失、结果不确定；成功、部分成功、失败和 unknown；报告、下载、审计、回执以及同一请求的重复提交。

所有记录使用一次性 `run_id` 前缀和固定 UTC 时间窗。合成记录不得伪装成现场采集；报告必须标注 `synthetic`。生成前记录基线行数和摘要，清理后再次核对，避免只删除主表而残留任务、回执、审计或制品。

### 3.3 真实目标 fixture

每种目标引擎至少准备：

1. 一个专用只读账号和一个按动作白名单授权的效果账号；账号不得访问业务 schema。
2. 一个可整体重建的 fixture 数据库/schema，包含正常、慢查询/锁等待、容量阈值、无权限、连接拒绝和数据变化场景。
3. 基线快照或初始化清单，能在每轮前恢复到同一状态。
4. 唯一对象前缀、允许写入的对象清单、预期副作用和清理 SQL 的评审记录。
5. 目标指纹校验：引擎、版本、server/database identity、账号、fixture 名称均匹配后才允许效果动作。

仓库当前测试目录没有统一的 conftest 夹具文件，夹具分散在测试文件中，不能假定存在全局隔离保护。尤其 `backend/tests/test_requirement_mysql_acceptance.py` 会对名为 `mesdbtools_requirement_verify` 的 loopback MySQL schema 执行 `drop_all/create_all`；`MESDBTOOLS_MYSQL_TEST_URL` 只有在操作者再次确认 loopback、固定测试 schema、无业务数据后才能注入。其他 `*_TEST_URL` 用例也应先审查各文件的拒绝条件。真实巡检测试可能用 SQLite 保存平台状态、仅连接真实目标引擎；它只能形成“真实目标采集”的部分证据，因为没有独立 MySQL 控制库，也没有同时证明真实模型和完整回执链，不能登记为 L4 完整闭环。

清理按“先停止 worker → 等待在途任务进入终态或人工对账 → 导出证据 → 按 `run_id` 删除制品/任务/回执/审计 → 恢复目标 fixture → 核对基线摘要”执行。只有白名单 disposable schema 可整体删除；执行前必须重新断言主机、端口、库名和用途。任何身份或目标不一致立即停止，不尝试自动纠正。

## 4. 严格执行顺序

以下顺序不得跨级补绿。每一步先保存候选提交、构建摘要、配置摘要、执行人、开始/结束时间和原始退出码。示例中的 `<python>`、`<base-url>`、环境变量名是执行位；秘密只通过受保护的进程环境或秘密管理器注入，不写入文档、命令参数、报告、截图或 shell 历史。

### 4.1 阶段 0：冻结范围与安全前置

- 冻结 R01-R12、D01-D18、TC001-TC116 的版本映射和必测标识；不能用总数代替逐项状态。
- 固定 Git commit、依赖锁文件、前后端制品摘要、数据库迁移清单、模型 provider/model 标识与 prompt/contract 版本。
- 核对当前环境是 E0-E4 中哪一类；分别登记控制库和目标库。
- 清空非本阶段需要的目标/模型环境变量，防止隔离测试意外触达外部系统。
- 为真实模型、真实目标动作、平台库迁移、完整备份恢复和生产灰度分别确认授权范围。授权必须含环境、实例/库、动作、时间窗、数据处置和责任人。

### 4.2 阶段 1：L1 静态、单元与构建

在未注入真实目标和真实模型秘密的环境中执行仓库现有入口：

```bash
<python> scripts/check_all.py --fast
<python> -m pytest -q -p no:cacheprovider
npm --prefix frontend run test
npm --prefix frontend run build
```

`scripts/check_all.py --fast` 会执行文档、合同、后端静态、运行时 schema、前端静态和 `git diff --check` 等检查，但跳过前端生产构建，因此生产构建必须单独运行。pytest 的默认发现范围来自根目录 `pytest.ini` 的 `backend/tests`。若有依赖真实环境而跳过的测试，应逐项记为 `not_run` 或转入 L2-L4，禁止把“pytest 总体退出 0”解释为这些用例已通过。

阶段停止条件：任一静态、构建、单元或秘密扫描失败；测试收集异常；必测用例 skip/xfail；工作区和候选提交不一致。

### 4.3 阶段 2：L2 控制库 schema 与 MySQL 服务集成

先对 E1 的隔离 MySQL 控制库执行。连接串只放在受保护的环境变量中；输出只保留脱敏后的 target summary。

```bash
<python> scripts/migrate_schema.py status
<python> scripts/migrate_schema.py check
```

`status` 用于读取迁移状态。`check` 只能在控制库身份已核对后执行；它不是备份命令，也不替代迁移授权。仅当该库可丢弃或已经完成并验证备份、所有应用写入已停止时，才允许：

```bash
<python> scripts/migrate_schema.py apply --backup-verified --service-quiesced
<python> scripts/migrate_schema.py check
```

两个参数只是操作者声明，脚本不会代做备份或停写。MySQL DDL 可能部分提交；失败后先核对真实结构和 `app_schema_migration`，不得盲目重跑或删除迁移记录。验收至少检查 `db_capability_effect_receipt` 的表、索引、约束、迁移 journal、旧数据行数/摘要和重复 `apply` 的幂等性。

隔离 MySQL 回归只在再次确认测试 URL 指向 disposable schema 后执行，例如：

```bash
<python> -m pytest -q -p no:cacheprovider backend/tests/test_requirement_mysql_acceptance.py
<python> -m pytest -q -p no:cacheprovider backend/tests/test_plan_governance_mysql.py backend/tests/test_plan_queue_mysql.py
```

这些用例会读 `MESDBTOOLS_MYSQL_TEST_URL`，连接值不应出现在命令文本或报告中。不得把 2026-10-25 的 8800 服务健康当作本阶段通过；当前实际控制库缺表和缺迁移记录是发布阻断项。

### 4.4 阶段 3：L2 真实 HTTP、worker 与持久回读

使用 E1 MySQL 控制库启动候选后端和 worker；模型/collector 如使用 stub，必须在执行记录中明确。先执行只读探针，再执行会产生状态的服务用例：

```bash
<python> scripts/check_api_smoke.py --strict --base-url <backend-base-url>
node scripts/check_frontend_smoke.cjs --base-url <frontend-base-url> --check-health
```

认证密码由 `MESGUARD_SMOKE_PASSWORD` 注入。`check_api_smoke.py` 只探测 OpenAPI 中安全的无参数 GET 路由；仍需审阅报告中的实际路径。`check_frontend_smoke.cjs` 只证明首页、静态资源和代理健康，不是浏览器功能验收。

`scripts/check_diagnosis_smoke.py` 会创建真实诊断事故，`scripts/check_all.py --diagnosis-smoke` 也会触发该写入；只有在 disposable 控制库且目标实例已明确时才可运行。不得把它放进无条件 smoke 命令。本阶段证明 HTTP、worker、队列和 MySQL 持久回读，不把页面行为计为 L2 通过。

### 4.5 阶段 4：L3 真实浏览器与实际组件路由

在候选前端、候选后端、真实 worker 和 E1 独立 MySQL 控制库上，使用真实浏览器执行第 6 节。请求必须经过实际组件、路由和 HTTP 接口，不能用组件函数直调或 Node DOM 替代。若用例只验证 UI，模型或 collector 可以明确 stub；结论必须注明被 stub 的边界，不得延伸为真实理解或真实采集已通过。

### 4.6 阶段 5：L4 真实模型与真实目标完整闭环

L4 使用 E2 或经批准的 E3：独立 MySQL 控制库、授权真实模型、真实目标 fixture、实际 collector/执行器、worker、审计和执行回执同时在线。关键边界不得 stub。

#### 4.6.1 真实目标引擎

按“只读连接 → 读取能力 → 效果动作预检 → 独立审批 → 执行 → 持久回读 → 清理”逐引擎执行。所有 host、port、service/database、user、password 都要显式从秘密环境注入，不使用测试文件中的默认地址。现有专项入口包括：

```bash
<python> -m pytest -q -p no:cacheprovider backend/tests/test_inspection_mysql_live.py
<python> -m pytest -q -p no:cacheprovider backend/tests/test_inspection_postgresql_live.py
<python> -m pytest -q -p no:cacheprovider backend/tests/test_inspection_oracle_live.py
```

还需按 TC001-TC116 中的引擎矩阵补齐 SQL Server 以及各动作族；没有现成安全入口时，先开发并评审 fixture 和拒绝条件，不能在现场临时拼接脚本。上述 inspection 专项测试若仍以 SQLite 保存平台状态，只能作为真实采集的部分证据；必须把同一能力接入独立 MySQL 控制库、真实 worker、审计和回执后，才能组成 L4 证据。每个动作必须同时核对目标库原生结果、平台任务终态、审计、执行回执和页面展示。连接失败、权限不足、超时、结果不确定必须明确失败或 unknown，不能返回安静成功。

#### 4.6.2 真实模型最小评测

按第 5 节冻结语料和指标后，在授权的 E2 或 E3 模型配置上执行。模型输出只生成候选决策，服务端仍负责能力、引擎、范围、参数、风险和审批校验。模型错误不得直接落成动作。真实模型选择必须继续进入现有能力并在真实目标 fixture 上产生可核对结果；只评模型 JSON 不构成 L4 完整闭环。

### 4.7 发布阶段 P：升级、恢复、灰度和长稳

L1-L4 通过后，完成第 7 节演练，并对同一最终候选执行必要回归和 168 小时长稳。P 是发布过程，不改变 L1-L4 的定义。仓库现有长稳入口为：

```bash
<python> scripts/soak_probe.py --base-url <frontend-base-url> --hours 168 --out reports/release-gate/soak.json
<python> scripts/release_gate.py --evidence reports/release-gate
```

应按冻结的负载包重复 `--path` 并用 `--token-env` 提供令牌；默认单一 `/health` 只能证明探针所覆盖的 HTTP 面，不能单独证明 R01-R12 的业务长稳。168 小时是既有发布要求，不得用几分钟 smoke、24 小时或修改 `--expect-hours` 代替。影响运行语义的代码、迁移、依赖或配置改变后，长稳计时重新开始。

当前 `scripts/release_gate.py` **只**读取 `static.json`、`local-http.json`、`real-engines.json`、`soak.json`。它没有 `requirement` tier，也不读取 R01-R12/TC001-TC116 矩阵。D17 的交付项包括实现 requirement gate、测试其失败关闭、接入发布入口并产生可审计结果。在 D17 完成前，发布负责人可以人工核对需求矩阵用于准备、发现缺口和决定继续测试，但总发布结论必须保持 blocked；人工核对不能替代 gate，也不能用于生产放行。

## 5. 真实模型评测设计

### 5.1 语料与重复

冻结不少于 60 条互不重复、确实需要模型理解的用户表达，每条对同一候选模型独立运行 3 次，总计至少 180 次真实调用。60 条按**可理解意图类别**分层，不按 R01-R12 机械均分，因为迁移、备份和发布操作并不都是模型语义。语料至少覆盖：信息读取与状态查询、巡检与诊断、报告生成、监控与告警、受控效果动作、多步骤/多目标请求、四引擎区分、同义表达和口语/错别字、参数完整与缺失、歧义澄清、越权范围、高风险/需审批动作、明确不支持的要求。各类别数量由评测评审按线上意图分布和风险冻结；不得在看到结果后删除失败样本。

每条金标至少包含：意图类别、关联需求 ID、期望 `decision/action`、允许的 capability 集、允许的引擎、目标范围、必填参数、缺参时应追问项、风险等级、是否需审批和禁止动作。真实模型原始返回需脱敏保存，并关联 contract/prompt/model 版本、调用时间、延迟、token/费用和最终服务端判定。

另建独立的**安全故障集**，覆盖未配置 API、provider 不可用/超时、malformed JSON、unknown capability、越权 capability、额外字段、超限输出和 schema 不匹配。安全故障由配置切换或受控响应注入产生，用于验证服务端失败关闭，可在 L1-L3 使用明确 stub；它不是 L4 真实模型理解样本，不计入 60 条 × 3 次及其准确率分母。无 API 专业页导航也在该安全集中验收。

### 5.2 指标必须分开报告

不得用一个“总体准确率”掩盖危险错误。至少分别报告：

| 指标 | 计算口径 | 发布意义 |
| --- | --- | --- |
| 正确动作选择 | action/capability 命中金标允许集的次数 / 可判定次数 | 是否理解用户真正要做什么 |
| 合法结构返回率 | 通过响应 JSON/schema 校验的真实返回次数 / 应返回结构化决策的次数 | 至少 99%；关键业务样板及原 invalid_output 回归必须全部合法并继续到预期步骤 |
| 原始模型候选的引擎与目标范围准确率 | 模型候选中的 engine、instance、scope 全部命中金标 / 对应次数 | 衡量模型候选质量；不等于实际派发可容忍错误 |
| 参数完整性 | 完整参数正确；缺参时准确追问且不执行 | 是否会猜参数或带缺参数执行 |
| 风险与审批 | 风险级别、审批要求、预检要求全部正确 | 是否绕过人工接管和保护 |
| 三次稳定性 | 同一输入三次均落入同一允许结果集 | 是否存在不可控漂移 |
| 实际派发正确性 | 服务端校验后实际 capability、engine、instance、scope、权限和审批全部正确 / 实际派发次数 | 必须 100%；误执行次数必须为 0 |

**拟定冻结阈值（尚未达成、需评审确认）：**真实模型 180 次中，所有标记为关键安全的语义样本在引擎/范围、缺参不执行和风险/审批上必须 100%；出现一次错目标、越权、绕审批或错误副作用即阻断。仅对非关键语义样本，建议原始模型候选的正确动作选择不低于 95%，引擎与目标范围准确率不低于 98%，参数/追问不低于 98%，三次稳定性不低于 95%。这些候选阈值不允许关键失败被总体平均数抵消。无论模型候选指标多少，服务端实际派发的引擎、目标范围、权限和审批必须 100% 正确，误执行必须为 0；被拒绝、要求澄清、不支持或无效返回只计“正确拒绝/失败关闭”，不能计作业务执行成功。独立安全故障集要求全部 100% 失败关闭；无 API 时必须 100% 导航到正确专业页，且导航零执行副作用。阈值确认后写入不可变评测清单，不允许为通过而临时下调。

2026-10-23 的 `invalid_output` 是待修复并复测的事实，不得计作通过。本轮不实际调用模型；真实调用需在执行前取得模型 provider、数据外发范围、语料脱敏、费用上限和时间窗授权。

## 6. L3 真实浏览器验收与缺陷循环

Node 测试、静态 HTML 探针和 API 测试不能替代真实浏览器。至少在项目支持的桌面浏览器及一档窄视口中，以 requester、approver、reader 三种身份执行适用的 TC001-TC116。每条用例从用户可见入口开始，覆盖：

- 有模型：输入需求、澄清、目标确认、计划冻结、审批、执行进度、取消/接管、完成/部分/失败结果、报告与回执回读。
- 无模型：按合同导航到匹配的专业页，显示可手工完成的参数和步骤；导航不得自动提交、创建计划、触发网络写请求或改变业务状态。后续动作必须由用户在专业页明确发起。
- 刷新、返回、重复提交、双标签页、会话撤销、worker 重启、超时和断网恢复；页面状态必须与服务端持久状态一致。
- 错目标、无权限、缺参数、失联目标和无效模型返回；不能显示虚假成功或用空结果替代失败。

每条执行证据保存为一个独立记录，字段至少包括：`case_id`、需求/任务 ID、候选 commit 与制品摘要、环境、控制库/目标库脱敏标识、浏览器版本与视口、账号角色、UTC 起止时间、前置数据摘要、用户操作、预期/实际结果、HTTP request/correlation ID、plan/batch/execution/receipt/artifact ID、目标库前后摘要、审计查询、截图/视频、console/network 错误、清理结果、执行人和复核人。截图不得暴露秘密；仅有截图而无服务端和数据库关联证据，不能证明效果动作成功。

缺陷级别：

- **S0**：数据破坏、越权、错目标执行、秘密泄露、无法恢复；立即停止全部验收并隔离环境。
- **S1**：绕审批、重复副作用、虚假成功、关键链不可用、迁移/回退失败；阻断功能关闭和发布。
- **S2**：主要路径错误或无可接受绕行、证据/审计缺失；阻断相关需求和发布。
- **S3**：不影响正确性和控制权的次要显示/易用性问题；记录处置决定，不能用 S3 降级掩盖数据或状态错误。

循环固定为“建单并绑定失败证据 → 修复 → 针对性复测 → 同需求全用例回归 → 相邻风险域回归 → L1 门禁重跑 → 更新候选摘要”。S0/S1 修复后还必须重跑受影响的 L2/L3/L4，以及发布阶段 P 中受影响的迁移、恢复或长稳。只有同一候选上的原失败用例和回归均通过才可关闭缺陷。

## 7. 发布阶段 P：升级、备份恢复、灰度与回退

### 7.1 执行前置与审批边界

此前“真实模型请求”和“实际库完整备份”均被自动审批拒绝。本分册只列操作前置，不在本轮重新申请或执行。后续必须先取得明确授权：

- 真实模型：provider/model、发送字段、脱敏规则、调用次数/费用、时间窗、日志保留。
- 实际平台库：精确实例和库、备份目录/保留、是否允许停写、恢复落点、维护窗口、RPO/RTO、执行人与复核人。
- 真实目标效果动作：精确实例/schema、动作白名单、最大影响量、审批人、停止/回退方法。

连通性、现有凭据或健康检查不构成这些授权。无授权时标记 `blocked`，不得以隔离测试替代后改为 passed。

### 7.2 升级与恢复演练顺序

1. **版本和身份检查**：记录旧/新应用版本、commit、制品摘要、Python/Node、MySQL server 版本、控制库 identity、字符集/时区、现有 migration journal、关键表结构和行数摘要。发现目标不符立即停止。
2. **完整备份**：对整个平台控制库做一致性备份，包含 schema、数据、触发器/事件、账号授权所需记录和恢复说明；计算摘要并由第二人验证可读。只导出新表或迁移相关表不算完整备份。
3. **隔离恢复演练**：把备份恢复到新的隔离 MySQL 实例/库，运行结构检查、行数/摘要、关键登录和历史任务回读。仅“备份命令成功”不能证明可恢复。
4. **停写**：停止所有 API 写入口、worker、scheduler、后台消费者和其他连接方；确认队列无未决认领，未确定副作用完成对账；保持只读健康面。仅停主 Web 进程不算停写。
5. **迁移**：在再次核对控制库 identity 后执行 `status`、`check`、带两个声明参数的 `apply`、再次 `check`。保存脱敏输出和退出码；核对新表、索引、约束、journal、旧数据摘要及幂等性。
6. **候选启动**：以普通迁移关闭模式启动新版本；先验证 readiness、worker、队列、登录、审计和历史数据，再跑只读 smoke，最后跑受控写路径。
7. **升级后恢复演练**：在隔离落点恢复升级前备份，使用旧版或明确兼容的恢复版本验证可启动和关键数据可读；同时模拟升级后新增任务、审批、回执和报告，验证回退方案能在批准的 RPO/RTO 内保留或迁移这些增量记录。`migrate_schema.py` 不提供通用 down；不得靠删除 journal、删表或换旧二进制伪装 schema 回退。

MySQL DDL 可能部分提交。迁移失败时冻结写入，保存现场，比较结构和 journal 后决定补迁移或从验证过的完整备份恢复；不得直接重复 `apply` 猜测会整体回滚。

### 7.3 灰度与回退

灰度按三个独立人工晋级阶段执行：内部测试账号和专用 fixture；受限用户及明确的非生产/低风险目标集合；批准范围内的生产目标。每阶段都重新核对候选摘要、错误率、队列积压、执行回执完整性、模型拒绝率、错目标/重复副作用、数据库负载和人工接管能力。具体比例、观察时长、流量和实例名单在变更单冻结，本分册不虚构固定数值。

出现 S0/S1、错目标、越权、重复副作用、回执缺失、迁移异常、数据摘要漂移、无法接管或关键指标越线，立即停止晋级并冻结新动作。回退前先保存当前新库的一致性备份、增量时间窗、binlog/变更证据和未决任务对账，避免恢复升级前备份时丢失灰度期间新增历史；该要求同时用于 TC109 的任务保留验证。

回退优先采用兼容 schema 的应用版本回退，保留当前控制库及其全部新增历史。只有应用无法与当前 schema 安全兼容时，才允许在**新建的干净控制库**恢复升级前备份；切换前必须把灰度期间新增的任务、审批、执行回执、报告、审计和其他增量记录按已评审方案保留或迁移，并验证主外键、摘要和可回读性。允许重放的是幂等的数据迁移，不是数据库运维、通知、切换或其他业务效果动作；业务效果只做状态对账，禁止为补历史而再次执行。整个过程必须满足变更单批准的 RPO/RTO。若没有可验证的方法保留这些新增记录，或预计超出批准的 RPO/RTO，回退必须阻断并保留原库，不得覆盖、原地恢复或销毁唯一证据。

完整回退顺序为：禁止新计划/审批 → 停止 worker 认领 → 对账已开始动作 → 保存新库和增量证据 → 优先回退应用 → 必要时在新库恢复并迁移增量 → 验证任务/审批/回执/报告/审计及目标侧状态 → 切换流量。不得在不清楚外部副作用时自动重放。
