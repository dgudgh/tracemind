# 客户一句话需求交付：完整开发任务分册

制定日期：2026-10-25。本文只定义开发工作，不代表任何任务已经完成，不授权调用真实模型、业务数据库或现场采集器，也不授权迁移、重启、部署或危险操作。后续实现应优先修复、接线和补测现有能力，不能另造一套执行器。

## 1. 交付目标与事实基线

目标产品行为只有一条主线：客户输入一句自然语言需求；有可用且获准调用的模型 API 时，模型只负责理解意图并从服务端发布的能力卡或固定流程中提出候选，服务端继续校验目标、参数、权限、审批、版本和执行条件，然后调用现有后台能力并展示真实结果；没有模型 API、模型失败或无法可靠理解时，系统打开有权限的专业页或手工能力表单，由用户点击后再执行。单纯导航在任何情况下都必须零业务执行。

完成口径按结果分层，不能混用：

| 类型 | 可以对客户声明的状态 | 关闭条件 |
| --- | --- | --- |
| 导航 | 已打开专业页面，等待手动操作 | 页面、账号和实例上下文正确；打开阶段零执行 POST、零计划、零业务副作用 |
| 仅方案能力 | 已生成操作方案，尚未执行变更 | 方案内容和限制可回读；`execution_blocked=true`；不得显示业务操作成功 |
| 读取能力 | 查询完成／失败／部分／待核对 | 真实读取处理器结束，持久结果与目标一致，缺证据不能算成功 |
| 效果能力 | 已完成／失败／部分／待核对 | 审批、队列、真实 handler、领域证据、不可变回执和结果发布全部一致 |
| 批量或固定流程 | 批次或流程的真实聚合状态 | 每个冻结目标、每一步和业务结果均可回读；任一未知不能汇总成全部成功 |

2026-10-25 的已知基线来自只读复核记录，开发开始时必须由 D01 重新确认：本地页面和 8800 健康接口虽返回 HTTP 200，但 8800 仍是旧进程；平台元数据库为 MySQL 8.0.40，缺少 `db_capability_effect_receipt`，迁移 `20261023_01_capability_effect_receipt` 未应用；2026-10-23 的真实模型调用以 `invalid_output` 结束，尚未关闭；现有需求验收中的报告模型和部分 Oracle 采集由替身提供。健康接口、mock 模型、mock collector、能力登记或计划创建都不能替代业务完成证据。

任务只能使用三种初始状态：`待实施` 表示方案已明确但尚未做；`待复核` 表示已有实现或历史材料，必须按当前源码和环境逐项重验；`受外部条件阻塞` 表示代码工作可以准备，但关闭还需要真实 provider、环境授权、迁移窗口或部署条件。任何状态都不表示测试已通过。

## 4. 详细开发任务

### D01 版本／环境基线

**业务缺口。** 当前页面可访问、`/health/ready` 返回 200，只能说明旧运行进程和数据库连接仍可用，不能证明 2026-10-23 后的源码、效果回执表或客户需求链已经加载。开发、测试、运行、制品和现场版本没有形成可机器核对的同一基线。

**现有可复用文件／新增建议。** 复用 `backend/app/main.py`、`backend/app/core/config.py`、`backend/app/migrations/runner.py`、`scripts/check_runtime_schema.py`、`scripts/release_gate.py`、`docs/operations/release-lifecycle.md`、OpenAPI 与数据库 schema baseline。现有 `release_gate.py` 只有既定四层门禁，不能假定它已理解本需求的 TC、能力追踪或真实依赖证据；D17 需另补需求专项 gate/schema。健康合同无法承载时，可新增“运行构建信息”只读响应模型，名称在实现评审时确定，当前并不存在。

**具体开发步骤。**

1. 固定源码 HEAD、dirty 文件清单、前后端构建版本、Python／Node／MySQL 版本、进程 PID／启动时间／工作目录和配置摘要；配置摘要必须脱敏。
2. 为后端暴露构建提交、构建时间、应用版本、代码支持的 migration head 和实际 schema head；前端在诊断信息中显示其资源版本。
3. 将“数据库连接 ready”和“本次能力链 schema ready”分开；缺关键迁移时接口必须返回兼容性不足，不能只报健康。
4. 将平台 MySQL 8.0.40、旧 PID、缺表和未应用 revision 作为本批初始差距重新核对并保存只读证据。
5. 生成后续每次测试必须引用的基线编号；测试环境、预生产和现场分别记录，不互相替代。

**初始状态。** 待实施。

### D04 真实模型适配

**业务缺口。** 真实配置 `deepseek-flash` 的首次需求理解返回 `invalid_output`，当前只知道结构校验失败，不能用 mock 响应替代真实适配，也不能在模型失败后悄悄换 provider、重复扣预算或转成业务成功。

**现有可复用文件／新增建议。** 复用 `backend/app/services/ai_config.py`、`capability_dispatch.py`、`ai_degradation.py`、`backend/app/models/ai_provider_config.py`、既有 transport limit 和 provider boundary 测试。建议新增脱敏的“模型结构评测工具”和人工标注样本文件；它们是测试工具，不进入生产执行路径，文件名在 D17 冻结，当前不存在。

**具体开发步骤。**

1. 保存 provider ID、模型名、配置 revision、响应协议能力和本次授权，不保存 API key 或完整敏感 prompt。
2. 对 OpenAI-compatible 与 Ollama 的 JSON mode 做显式能力协商；同时接受经过严格边界处理的纯 JSON 和允许的代码围栏，拒绝解释性前后缀、截断、多对象和未知字段。
3. 将解析分成传输、JSON 解码、schema 校验和业务目录校验四层，日志只记录错误类型、字段路径、长度和脱敏摘要。
4. 对 `invalid_output` 建立可复现样例并调整 prompt／schema／适配器；禁止放宽到模型可生成任意 SQL、Shell、handler 或 DAG。
5. 固定单请求 provider 和预算；超时、响应过大、重定向、拒答、低置信和配置变化均安全降级，回查不二次调用。
6. 用人工标注中文用例评测真实 provider；效果能力只走到其现有风险策略要求的确认／审批门禁，实际执行另由对应任务验收。无审批要求的能力不凭空增加双人审批。

**明确验收条件。** 实际获准 provider 按[模型评测规则](acceptance-runbook.md#5-真实模型评测设计)冻结至少 60 条语料、每条 3 次，分层记录能力、引擎、目标、参数、风险与稳定性。合法结构返回率至少 99%，关键业务样板及原 invalid_output 回归必须全部通过；其他候选质量达到手册阈值，实际派发正确率 100%、误执行为零。真实失败样例有原因和处理结论；任何模型成功都不被当作业务 handler 成功。

**责任／依赖／工作量。** AI 后端主责，测试、安全／运维共同验收；依赖 D01-D03；L。

**测试关联。** TC009-TC020、TC111-TC116。

**交付物。** provider 兼容矩阵、结构适配器、脱敏诊断字段、真实模型评测报告和限制清单。

**初始状态。** 受外部条件阻塞；关闭需要用户授权的真实 provider 调用和可用配置，本计划阶段不调用。

### D05 引擎目标范围

**业务缺口。** “当前数据库”“MySQL”“不要 Oracle”“所有数据库”等表达必须与当前实例、账号授权、能力支持引擎联合求交。单实例上下文不能把“所有”静默缩成当前 MySQL，引擎否定词不能被当作允许目标，MySQL 页面也不能展示 Oracle 专属卡片或示例。

### D07 只读执行

**业务缺口。** “读取已存结果”“对目标做即时只读查询”和“创建采集／同步任务”是三种不同业务动作。读取卡必须调用对应的真实现有查询 handler，并正确表达真实空结果、采样失败、缺证据、部分结果和过期数据；不能用空数组、mock collector 或模型文本制造成功。锁等待等实时读取可以调用受限的只读采样适配器，禁止的是把读取请求偷偷升级为异步采集任务、来源同步或业务写入。

**具体开发步骤。**

**具体开发步骤。**

## 5. 实施顺序与并行关系

开发按以下门禁推进，不能因为某个示例先跑通就跳到发布：

1. **基线与真值。** D01 和 D02 先固定运行事实及逐卡范围。D03 可在 D02 主结构冻结后并行实现合同。
2. **理解与输入。** D04、D05、D06 并行推进，但 D04 的真实 provider 验收保持外部阻塞；没有真实模型时继续使用 D14 人工链。
3. **业务能力。** D07、D08、D09 按 D02 每张卡分别关闭。D08 源码接线、common v3 回执和隔离数据库验证可在 D15 前完成；实际 8800 运行验收等待 D15。读取、效果和 plan-only 三种口径不得互相借证据。
4. **控制与恢复。** D11、D12 是 D08 和 D10 放行的硬依赖；D10 只组合已经逐卡验收的能力。
5. **体验与证据。** D17 的工具骨架、fixture、结果 schema 和专项 gate 从 D01 起并行开发；D13、D14、D16 和测试内容随各任务增量完成，最终由 D17 汇总分层证据。
6. **环境与交付。** D15 在 D08 存储变更候选冻结后先做隔离验证，再在授权窗口内升级并核对实际 8800；D15 不等待 D08 全任务关闭，D08 的运行验收反向等待 D15 闭环。D18 只发布逐卡通过范围。

首批纵向样板也必须包含：统一入口合同、正确目标／补参、实际发布的只读卡、完整无模型手工路径、权限、幂等恢复、客户结果 UI、迁移／版本门禁和真实模型或明确关闭模型后的验收。MySQL 单卡、批量和报告只用于尽早验证整条链，不能缩小最终范围或关闭总需求。所有已承诺能力必须经 D02 盘点并逐卡通过对应门禁；报告、17 张效果卡、批量和固定流程不能留在“已登记”状态，暂无业务执行器的卡必须作为未完成阻塞项留在交付清单中。

## 6. 任务关闭和发布门禁

每个 D 任务关闭时都要记录：实际修改文件与版本、适用能力／引擎／账号、执行的 TC 编号、命令或场景、通过／失败／跳过、证据位置、替换的依赖、未完成项和验证日期。只有真实执行过的测试才能标记通过。

每张能力卡的发布门禁至少包含：

- 目录、版本、schema、引擎、权限、风险和人工入口一致；
- 模型只选择服务端允许对象，失败安全转人工；
- 目标与参数冻结，确认审批不能被绕过；
- 调用现有 handler，队列与 execution 可恢复；
- 结果有真实领域证据，效果有不可变回执，plan-only 不冒充执行；
- 客户 UI 可回读相同目标和结果；
- 对应自动化、真实依赖、迁移、制品和运行版本证据齐全。

任何一项缺失时，该卡保持待实施、待复核或受外部条件阻塞。源码完成、测试完成、构建完成、迁移完成、运行加载和客户现场验收分别记录，不能合并成一个“已完成”。
