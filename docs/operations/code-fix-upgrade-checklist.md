# 安全修复升级检查单

## 适用范围

本次修复涉及授权、会话撤销、归档预检与审批、归档密钥轮换、Oracle 备份校验和平台结构迁移。代码和自动化测试不等于客户现场升级或恢复验收；不要直接替换正在运行的程序后跳过下列检查。

这不是其他客户环境已迁移的证明；新现场仍必须逐项执行下述流程。证据及清理边界见

## 升级前

1. 备份平台外置数据库，核对备份成功、目标库和恢复方式。备份配置、JWT 签名密钥、当前与历史归档密钥；不得将密钥写入代码仓库。
2. 停止所有平台写入进程、调度器和后台任务。保留旧版本安装包或镜像、配置以及当前迁移版本。
3. 核对非管理员账号的动作角色和资产范围。未授权账号、未知业务接口默认拒绝；已有角色不会自动恢复被撤销的权限。
4. 核对恢复 Agent 的显式权限及账号绑定，详见 [认证与会话安全](../backend/auth/auth.md)。

停服务前先执行下面的 `status`、`check`，识别待迁移项、目标库、权限和备份工具是否可用。
端口或 `/health` 可达不能替代版本检查。本次曾因未提前核对待迁移版本而在重启时被阻断，后续不得再把普通重启当作迁移预检。

## 平台数据库迁移

新增待发布迁移：`20260911_01_sql_history_identity` 为 SQL 历史增加可空 schema、目标指纹与目标快照，为 SQL 画像增加可空目标指纹，保留全部旧行。本轮只在隔离 SQLite 验证，**未应用到当前平台库**；不要因下文此前 BIGINT 迁移已完成而直接重启。具体边界见[架构缺陷修复记录](../archive/acceptance/2026-09-11-architecture-bug-fixes.md)。

外置 MySQL/PostgreSQL 默认只检查结构，不在普通启动流程中自动升级。SQLite 仅在开发、测试和本地打包等指定模式下默认自动迁移。需要升级或结构漂移时启动失败，不以继续运行掩盖结构不一致。

在发行包根目录使用该版本对应的 Python 运行环境，预先通过受保护的环境设置 `DATABASE_URL`。不要把包含密码的连接串直接写入命令历史。

```bash
python scripts/migrate_schema.py status
python scripts/migrate_schema.py check
# 完成并验证备份、停止所有写入之后，才执行：
python scripts/migrate_schema.py apply --backup-verified --service-quiesced
python scripts/migrate_schema.py check
```

`check` 检查失败时返回非零退出码。两个 `apply` 参数只是运维人员对备份和停写的明确确认，脚本不会代替实际备份，也不会自动停止服务。脚本使用数据库级锁和迁移记录；MySQL DDL 可能部分提交，因此失败后应核对日志及结构，再决定重试或恢复备份。

结构回退不能仅靠换回旧安装包。应使用经验证的发行版回退迁移；没有对应回退脚本时，在维护窗口按备份恢复方案处理。此初始化脚本不提供通用 `down`，不会删除旧数据来强行兼容。旧 `db_check_result_new` 表复制后保留，确认数据和兼容性前不得自行清理。

### 慢 SQL 计数扩容

版本：`20260910_01_slow_sql_counters`；范围仅 `db_slow_sql` 的 `executions`、`logical_reads`、`physical_reads`、`rows_processed`。

- MySQL 将有符号 INT 扩容为 BIGINT，保留空值约束、默认值和注释；不新增表、不钳制或清空计数。
- 执行前检查全部字段定义；异常类型、无符号字段、生成列等不受支持的属性应阻断，不强行 MODIFY。
- 本机实际验证：229 张 InnoDB 表完整导出并校验，迁移前后平台表行数不变，73 条慢 SQL 的整行摘要不变；迁移记录新增一项。
- MySQL DDL 可能先提交、journal 后失败。遇到部分完成先核对四列和版本记录，再使用同一迁移的幂等路径，不盲目执行逆向 SQL。
- BIGINT 缩回 INT 可能截断大计数，现有迁移拒绝有表时的破坏性降级。回退旧程序需独立验证其对 BIGINT 和迁移记录的兼容性，不能删除版本行来伪装回退成功。
- 本机备份完成性与完整性已校验，但未进行恢复演练；其他 MySQL、MariaDB、PostgreSQL 环境不沿用本机通过结论。

### 迁移后的启动

显式 `apply` 和 `check` 成功后，以普通迁移关闭模式启动后端；本机使用 `TRACEMIND_AUTO_MIGRATE=0` 和端口 8801，前端仍为 3300。
至少核验进程归属、后端 `/health/ready`、前端代理 `/health/ready`、首页和静态资源。
就绪必须同时满足数据库和结构检查；失败时保留日志、停止后续发布，不以清空表、重置账号或放宽权限恢复“正常”状态。

## 归档与备份复验

- 旧的“已批准”任务需要对具体预检重新批准。批准绑定预检 ID 和证据摘要；重新预检后旧批准失效。执行行数上限必须与预检一致。
- 归档读取使用确定的主键排序和一致性快照，发布前复核选中数据及数量。缺少稳定主键、存储引擎或快照隔离不受支持时拒绝执行。SQL Server 需要预先启用快照隔离，平台不会擅自修改该数据库设置。
- 轮换 `ARCHIVE_ENCRYPTION_KEY` 时，将旧密钥按原 key ID 放入 `ARCHIVE_ENCRYPTION_KEY_PREVIOUS` JSON 映射。先验证新归档和历史归档均能读取，再按保留制度管理旧密钥；移除仍有制品依赖的密钥会导致这些制品无法解密。
- Oracle 校验绑定具体备份集和备份片清单，并检查文件哈希，不再用泛化校验代表某一份备份已可恢复。同机多个实例必须明确匹配 SID。远端需要 Python 3、SQL*Plus 和 RMAN；校验成功不代表已实际恢复，也不能据此宣称达成恢复时间目标。

## 验收重点

- 撤销会话、改密码和禁用账号后，另一进程持有的旧令牌应失效。
- 越权访问 URL、查询参数、请求体及间接任务关联的实例均被拒绝；合法角色的正常操作仍可完成。
- 数据变动、行数上限变化、重新预检或取消审批后，不允许用旧批准发布归档。
- 使用真实 MySQL/PostgreSQL 进行停写、备份、升级、重启以及失败回退演练；使用真实 Oracle 备份进行独立恢复演练。这些现场步骤不能用 SQLite 单元测试替代。
